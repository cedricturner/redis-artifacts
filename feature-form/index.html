Both hires read the same records. Their “average sales” still disagree.

One counts closed days. The other skips them. Same feature name, different calculation. Very smart people. Very different inputs.

This mismatch is training-serving skew. Her ML learned with one meaning of “average,” then used another.

The hires represent two workflows of one ML system: training and live use. They are not two models voting on an answer. Different predictions alone do not prove skew.

Feature Form manages the definitions and coordinates building the features on existing data systems. Redis supplies the live values quickly. The model still makes the prediction.

Consistent definitions do not mean frozen values. Average sales change as new sales arrive. The calculation should keep the same meaning.

03

Why features go wrong

  1. Duplicate work. Teams rebuild the same feature with slightly different rules.
  2. Training-serving skew. Historical and live feature pipelines disagree about how to calculate the input.
  3. Lost history. A definition changes and nobody can trace which version was used.

Feature Form gives teams shared, versioned definitions. They still need to choose useful features, check data quality, and test their models.

04

How Feature Form works

the real system
  1. Connect. Register providers, the connections to your data, compute, and Redis.
  2. Define. Describe features, transformations, labels, and training sets in a Python definitions file.
  3. Apply and build. Preview changes, then apply them. A saved definition is not proof that the build has finished.
  4. Train and serve. Training uses historical inputs paired with known outcomes. Live applications retrieve feature values through a feature view backed by Redis.

For an old training example, use only information available at that time. Using later sales to predict an earlier day would leak the answer.

05

Words you’ll hear

a quick reference
Entity
The thing a feature describes, such as a shop or customer.
Dataset
A registered table, view, or file. Raw data stays in your systems.
Transformation
A calculation that turns raw records into useful inputs.
Training set
Historical features paired with known answers, aligned in time.
Materialization
Computing feature values and writing them where they can be read.
Online store
Storage for quick live reads. Here, that is Redis.
Feature view
A named group of features an application can retrieve for an entity.
Workspace
A team or environment’s area for definitions, connections, and permissions.
Version
A saved revision of the resource graph, so changes can be traced.

Training fits the model. Inference uses it. Feature serving retrieves inputs; model serving makes predictions available to an application.

Continue the conversation

for Sales

Look for teams rebuilding features, struggling to keep training and live inputs aligned, or trying to serve fresh inputs quickly.

  • What prediction are you trying to make?
  • Where do the input data and calculations live today?
  • How do you keep historical and live feature logic consistent?
  • How fresh must features be, and how quickly must the application read them?
  • Which teams own the pipelines, model, and Redis deployment?

The handoff: “Feature Form helps you define, build, and reuse model inputs on your existing data stack, with Redis for live feature serving.”

What to validate in a technical follow-up

Confirm source and compute integrations, refresh requirements, model-serving integration, access controls, deployment, and licensing for the customer’s environment.
