RDI 101

Redis Data Integration

AKA RDI. Everyone keeps a copy of their data in Redis. The only argument is how the copy stays right.

TL;DR

Redis Data Integration keeps the copy of your data in Redis in sync with the database it came from.

READS FOR THIS DATA STOP GOING TO THE SOURCE DATABASE.

TWO REASONS PEOPLE NEED IT
01 the answer is wrong

The row changed at the source. Redis kept handing out the old one, and nothing in the data says so. The application acted on it anyway.

In the pie shop: you baked with fruit that molded three days ago, and you sold it.

02 the reads are too many

Postgres, Oracle and MongoDB will take writes all day. Reads at volume are the other direction. Push thousands a second at one and it does not fall over, it just answers slowly, which is the same as broken when somebody is waiting.

In the pie shop: a hundred orders at once, and every one of them means an hour's drive to the orchard.

RDI answers both, and it is the same mechanism either way. Every change arrives as it happens, so the copy is never behind and it never expires out from under you.

03

The two main issues

ISSUE ONE STALE ANSWERS MOLD YOU CANNOT SEE

How long are you willing to hand out the wrong answer?

Nothing told the fridge. Cache-aside has no channel for being told, because the only thing that triggers it is a request. You can build one, and plenty of teams do, but then the propagation is yours to write and yours to debug when it drifts.

CACHE-ASIDE

Check Redis first. On a hit, return it. On a miss, read the source, write the value into Redis, and return that. The application manages both sides. Also called lazy loading.

1   look in Redis
2   not there, so ask the database and wait
3   put a copy in Redis
4   throw that copy away in five minutes

STEP 4 IS A GUESS, AND THE DATA GIVES YOU NOTHING TO BASE IT ON

So why throw the copy away at all? Because nothing tells Redis when the database changed. With no signal to go on, the only move left is to re-read the source on a schedule. So you pick an interval, and the interval costs you either way.

READ IT MORE OFTEN your costs increase

Every refresh is another round of queries against the source. Turn the frequency up far enough and you are back to the load the copy existed to avoid.

READ IT LESS OFTEN you serve stale data

The copy drifts further from the truth between refreshes, and every read that lands in the gap is a wrong answer you handed out on purpose.

No interval gives you both. And unlike fruit, data does not tell on itself: a stale address looks exactly like a fresh one.

ISSUE TWO TOO MANY READS THE LUNCH RUSH

Everything above is about being wrong. This one is about being slow, and the slow thing is the source database itself.

A hundred people walk in at noon and every one wants blueberry. The orchard is an hour away, and no amount of planning fits a hundred trips into one lunch rush.

That is your source database. Postgres, Oracle and MongoDB take writes all day without complaining. Reads at volume are the other direction. Push thousands a second at one and it does not fall over, it answers slowly, and it answers slowly for everything else pointed at it. For an overnight report that is survivable. For somebody watching a map to see where their driver is, a late answer is the same as no answer.

So you stop asking it. Work out which part of the workload needs high-volume reads in real time, put that data in Redis, and let RDI keep it there. Those reads stop touching the source, and the source goes back to the job it is good at.

END OF THE ANALOGY No more fruit. Everything below is how RDI actually works.
04

How RDI works

names are from the Redis docs

One pipeline, two phases, no timers anywhere.

THREE STAGES INSIDE RDI. THE ONLY DATABASES IN THIS PICTURE ARE THE SOURCE AND REDIS.

  • No timers anywhere. Nothing expires, because changes arrive on their own.
  • You pick the shape. Source tables rarely match what an app wants to read. Transformations turn rows into the hashes or JSON documents your app actually wants. You set that up once in configuration.
  • Nothing gets lost. Redis guarantees at-least-once delivery. A change may land twice, which is harmless, because writing it again changes nothing.
05

How much reshaping you need

same pipeline, more work in the middle

How much reshaping do you actually need?

  • EASY One table, copied as-is. A product catalog read by ID. Rows become Redis hashes, keyed the way the app already asks. No reshaping. This is the five-minute version.
  • MEDIUM Several tables, joined into one object. A customer, their addresses, and their recent orders arrive separately and leave as one JSON document. The app reads it in a single call. The join happens in the pipeline instead of in your code.
  • HARD Everything, indexed and searched. Fraud scoring, personalization, anything that asks "across all of it, which ones matter." Cache-aside struggles here, because it only holds what somebody already asked for, so a search across the set answers from a partial picture.
06

Other ways to do this

checked against each vendor's own docs

There are three ways to do this without RDI. They differ in how much of the pipeline you end up operating, and in how fresh the copy can get.

ONE. ASSEMBLE OPEN SOURCE PARTS

Nothing to license, and it is the same architecture RDI uses. Everything that keeps it running is yours to build and carry.

WHATHOWDOWNSIDES
Debezium Open source engine that reads a database log and emits change events. The same collector that sits inside RDI. It only gets the changes out of the door. Transport, transformations, recovery and the writes into Redis are all yours to build.
Kafka plus a Redis sink Debezium lands change events in Kafka, then a sink connector writes them into Redis. Redis Field Engineering, Confluent and Lenses each publish one. You now run Kafka. Brokers, topics, retention, rebalances and the pager at 3am belong to your team.

TWO. BUY A MANAGED PRODUCT

Somebody else runs the infrastructure and the bill arrives monthly. Designing the pipeline is still your job.

WHATHOWDOWNSIDES
Managed Kafka Confluent Cloud and services like it run the brokers for you and offer the same Redis sink connector. Another vendor and another bill, and you still design the pipeline, the transformations and what happens when the target disappears.
Airbyte Integration platform with an official Redis destination connector. Data lands on a sync schedule. Freshness is capped by the schedule, so you are back to serving stale data, just with a longer window than a five minute timer.

THREE. BUILD IT YOURSELF

Nothing new to install and no new vendor. What you save in setup you pay back in drift, staleness, or slower writes.

WHATHOWDOWNSIDES
Your own application code Cache-aside, or writing to the database and Redis in the same request. You own the round trip and the expiry guess. Dual writes drift apart the first time one succeeds and the other fails, and Redis only ever holds what somebody happened to ask for.
A batch reload Any scheduler plus a script that loads the whole dataset into Redis in one batch. Your data is exactly as old as the last batch, and running it often enough to feel current gets expensive quickly.
Source database triggers The source database pushes rows out itself whenever they change. Application logic moves into your database, every write on the source gets slower, and it turns into the code nobody will touch.

Every route here works, and the first group is RDI's own. RDI is Debezium reading the log, Redis Streams carrying the events, and a processor writing the target. What it adds is that the checkpointing, the backpressure handling, the dead letter queue, and the at-least-once guarantee arrive already built and supported instead of becoming your team's on-call rotation.

07

Which databases it reads

source list from the docs, Aug 2026

Does RDI already read where your data lives?

SUPPORTED SOURCES

Oracle PostgreSQL MySQL MariaDB MongoDB SQL Server Spanner AlloyDB Aurora Neon Supabase Snowflake

Each source links to its setup page in the Redis docs. AlloyDB has no page of its own and is covered by the support table on the index.

Change tracking is switched off by default on every one of these, so the source needs preparing first. Oracle uses LogMiner, Postgres uses pgoutput, MySQL and MariaDB use the binlog, SQL Server uses its built-in feature, MongoDB uses change streams, and Spanner uses change streams too. If you run RDI yourself, Spanner and Snowflake need it on Kubernetes with Helm. On Redis Cloud, Snowflake is one of the managed sources and has to be hosted on AWS.

Three things to know before you start. RDI runs against Redis Cloud and Redis Software, not open source Redis. On Redis Software you install it yourself and it needs a commercial licence, and that licence includes two extra shards to run RDI's own database; on Redis Cloud it comes with a Cloud Pro subscription on AWS. And if your data lands in a warehouse before you want to serve it, Snowflake is the only one covered. Databricks and BigQuery are not supported.
