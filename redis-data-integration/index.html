What if the store stocked it for you?

names are from the Redis docs

What if you filled it once and it stayed filled?

THE RDI DATABASE IS NOT THE ONE YOUR APP TALKS TO. IT HOLDS THE CHANGE STREAMS ON THE WAY THROUGH.

  • No timers anywhere. Nothing expires, because changes arrive on their own.
  • You pick the shape. Source tables rarely match what an app wants to read. Transformations turn rows into the hashes or JSON documents your app actually wants. That is configuration, not app code.
  • Nothing gets lost. Redis guarantees at-least-once delivery. A change may land twice, which is harmless, because writing it again changes nothing.
05

What if you need more than a copy?

same pipeline, more work in the middle

How much reshaping do you actually need?

  • EASY One table, copied as-is. A product catalog read by ID. Rows become Redis hashes, keyed the way the app already asks. No reshaping. This is the five-minute version.
  • MEDIUM Several tables, joined into one object. A customer, their addresses, and their recent orders arrive separately and leave as one JSON document. The app reads it in a single call. The join happens in the pipeline instead of in your code.
  • HARD Everything, indexed and searched. Fraud scoring, personalization, anything that asks "across all of it, which ones matter." This is the case cache-aside cannot reach, because it never holds all of it.
06

What else could you do instead?

five real options

Every one of these works. The question is how much of it you want to own.

  • OPTION 1 Write it in the app. Cache-aside, the one from the start of this page. Free to begin and already in your codebase. You own the round trip, the expiry guess, and the fact that Redis never holds all of it.
  • OPTION 2 Write to both places at once. The app saves to the database and to Redis in the same request. Easy to explain in a meeting. It breaks the first time one write succeeds and the other fails, and no transaction covers both, so the two drift apart quietly.
  • OPTION 3 Reload everything on a schedule. A nightly job that dumps the dataset into Redis. Simple, and Redis is complete after it runs. Your data is as old as the last run, and running it often enough to feel fresh gets expensive fast.
  • OPTION 4 Put triggers on the source database. The database itself pushes rows out when they change. It is close to real time, and it puts application logic inside your database, adds work to every write on the source, and becomes the thing nobody wants to touch.
  • OPTION 5 Build the pipeline yourself. Debezium, a streaming layer, and a consumer you write. This genuinely works, because it is the same shape RDI uses. You now own a streaming platform: checkpoints so you can restart safely, backpressure for when the source outruns the target, replays, and every transformation.

RDI is option 5 with the plumbing already built. Same approach, same components, but the checkpointing, the backpressure handling, and the delivery guarantee come with it instead of becoming your team's problem.

  • Every source needs a switch flipped first. Change tracking is off by default. Oracle uses LogMiner, Postgres uses pgoutput, MySQL uses the binlog, MongoDB uses change streams, SQL Server uses its built-in feature.
  • Warehouse data is the honest gap. Snowflake is preview. Databricks and BigQuery are not supported. If a customer lands data in a warehouse first and wants to serve it live, say so early.
